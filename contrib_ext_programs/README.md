# ext.py

Скрипт сверяет версии внешних программ из `config.json` с версиями в SGML-документации Tantor. Результат пишется в `ext.txt` рядом со скриптом.

## Требования

- Python 3.6+ (используется только стандартная библиотека). Сеть не нужна.
- Локальный клон репозитория Tantor DB по пути из константы `TANTOR_DB_ROOT` (по умолчанию `/home/kot/repo/tantor-db-18_6/`).

## Входные данные

Источник `config.json` можно указать двумя способами (см. раздел «Запуск»):

1. Локальный файл `config.json` рядом со скриптом — поведение по умолчанию.
2. Произвольный путь к локальному файлу — первым аргументом командной строки или ответом на интерактивный запрос.

Если у вас приватный репозиторий — скачайте `config.json` через браузер (страница файла → `Raw` → «Сохранить как…») и передайте скрипту путь к сохранённому файлу.

Формат самого JSON (на верхнем уровне — словарь сущностей; читаются только указанные поля внутри `general`):

```json
{
  "pgbouncer": {
    "general": {
      "version": "1.25.1",
      "git": {
        "url": "https://github.com/pgbouncer/pgbouncer.git",
        "tag": "pgbouncer_1_25_1"
      }
    }
  }
}
```

Значимые поля для скрипта:

| Поле                   | Назначение                                               |
| ---------------------- | -------------------------------------------------------- |
| `general.version`      | Номер версии (выводится как есть, без преобразований).   |
| `general.git.url`      | URL git-репозитория.                                     |
| `general.git.tag`      | Тег/ветка релиза.                                        |

Любые другие поля в JSON игнорируются.

## Документация Tantor

Корень репозитория задаётся константой `TANTOR_DB_ROOT`. Из него читаются все `*.sgml` в корне двух каталогов (порядок как в `DOC_DIRS`):

```
tantor/doc/contrib_ext
tantor/doc/programs
```

Имя программы — имя файла без `.sgml` (например `ldap2pg.sgml` → `ldap2pg`). Версия берётся из начала файла:

```sgml
<emphasis role="strong">Version</emphasis>: 6.6.0
```

или с двоеточием внутри тега:

```sgml
<emphasis role="strong">Version:</emphasis> 26.1.21
```

Если строки Version в файле нет (как у `pipelinedb.sgml` или `pg_anon_old.sgml`), программа всё равно попадает в отчёт, но с пустой версией.

Подкаталоги (`*_source`, `*_target`, `*_images` и т.п.) не обходятся.

Чтобы сменить корень репозитория или набор каталогов — отредактируйте `TANTOR_DB_ROOT` / `DOC_DIRS` в начале `ext.py`.

## Список обрабатываемых сущностей

Из `config.json` скрипт читает только сущности из жёстко зашитого списка `ENTITIES` (в порядке вывода):

```
pipelinedb, pg_anon, pg_configurator, ldap2pg, mysql_fdw,
oracle_fdw, pg_timetable, pgbouncer, tds_fdw, wal-g
```

Сущности, которых нет в `config.json`, молча пропускаются. Лишние ключи в JSON в отчёт не попадают.

Блок документации заполняется всеми `*.sgml` из каталогов выше, а не только именами из `ENTITIES`.

Чтобы изменить набор или порядок сущностей `config.json` — отредактируйте константу `ENTITIES` в начале `ext.py`.

## Выходные данные

Файл `ext.txt` рядом со скриптом. Три секции, разделённые пустой строкой.

### `config.json:`

TSV-подобный текст: четыре колонки (имя, версия, git-URL, git-тег), разделённые табуляцией, с выравниванием по ширине. Порядок строк соответствует `ENTITIES`. Отсутствующие значения (например, `tag`) выводятся пустой строкой.

```
<name>    <version>    <git_url>    <git_tag>
```

### `tantor doc:`

Две колонки: имя программы и версия из sgml. Сначала файлы из `contrib_ext` (по алфавиту), затем из `programs` (по алфавиту).

```
<name>    <sgml_version>
```

### `Версии отличаются в:`

Программы, у которых версия есть и в `config.json`, и в sgml, но номера не совпадают:

```
<name> json=<json_version> sgml=<sgml_version>
```

Если у одной из сторон версии нет — строка в этот блок не попадает.

Пример:

```
config.json:
pipelinedb     	1.4.2  	ssh://git@gitlab.example.com/database/pipelinedb.git	
pg_anon        	1.11.0 	https://github.com/TantorLabs/pg_anon.git                   	1.11.0
pg_timetable   	7.1.0  	https://github.com/cybertec-postgresql/pg_timetable.git     	v7.1.0
wal-g          	3.0.9  	https://github.com/wal-g/wal-g.git                          	v3.0.9

tantor doc:
ldap2pg     	6.6.0
pg_timetable	7.0.0
wal-g       	3.0.8
pg_anon     	1.10.3
pipelinedb  	

Версии отличаются в:
pg_anon json=1.11.0 sgml=1.10.3
pg_timetable json=7.1.0 sgml=7.0.0
wal-g json=3.0.9 sgml=3.0.8
```

## Запуск

### Из терминала

Без аргумента — будет интерактивный запрос источника (Enter без ввода → локальный `./config.json`):

```bash
./ext.py
```

С явным аргументом — путь к локальному файлу:

```bash
./ext.py /path/to/config.json
./ext.py ~/Downloads/config.json
```

Скрипт сам переключает рабочий каталог на папку, где он лежит, поэтому его можно вызывать из любой директории — выходной `ext.txt` всегда создаётся рядом со скриптом.

### Через двойной клик в файловом менеджере

Файл уже настроен под запуск из штатного файлового менеджера Ubuntu (есть shebang `#!/usr/bin/env python3`, бит исполняемости установлен, переводы строк LF). Двойной клик → выбрать `Run in Terminal` (или «Запустить в терминале») — откроется окно, скрипт спросит источник, и после завершения попросит нажать Enter, чтобы окно закрылось.

При запуске без терминала (`Run`) интерактивный запрос показать негде, поэтому будет использован локальный `./config.json`.

## Поведение и ограничения

- Скрипт работает только с локальными файлами и не делает никаких сетевых вызовов.
- При любом исключении (нет файла, битый JSON, ошибка прав и т.п.) выводится traceback, и скрипт всё равно ждёт нажатия Enter — ошибку успеешь прочитать.
- Если очередная сущность из `ENTITIES` отсутствует в JSON — она просто не попадает в секцию `config.json:`, остальные обрабатываются как обычно.
- Если каталог из `DOC_DIRS` не найден, скрипт пишет предупреждение и продолжает с остальными.
- Ширина колонок в `ext.txt` подбирается под фактические данные текущего запуска, поэтому между запусками выравнивание может отличаться.
